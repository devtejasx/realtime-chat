## Load tests

`docker run --rm --network realtime-chat_default -v .../loadtest:/scripts:ro \
  -e BASE_URL=http://balancer:8080 grafana/k6 run /scripts/<scenario>.js`

Each scenario uses the arrival-rate profile defined in its own file, not a flat
VU count.

### Summary

| Scenario | Requests | Throughput | Error rate | Checks passed | k6 verdict |

Across the whole campaign both instances served 91,220 requests and returned
**zero 5xx** — `rtc_http_5xx_total` never appeared on either `/metrics`, meaning
the counter was never incremented. Every threshold breach below is latency under
saturation, not failure.

**Where it stopped scaling:** at roughly 65 req/s, CPU-bound on bcrypt. Both
instances sat near 500% CPU while using ~10 MB of memory each, and the arrival-rate
executor began dropping iterations. This is the intended cost of the password
hash, not a defect — but it does mean authentication throughput, not messaging,
is what sizes the fleet.

**Where it stopped scaling, and on what:** ~242 req/s, and the limiting resource
was **PostgreSQL, not the application**. At saturation the database container held
~492% CPU while the two app servers together used ~260%. Every write in this
scenario lands on one conversation row — deliberately, since that is the worst
case for the `last_message_at` update — so this is the pessimistic shape. The
connection pool is 8 per instance (16 total), which is the first thing to raise
before concluding the database itself is the ceiling.

### websocket — up to 500 concurrent sockets, 45s hold

| Metric | Value |
| --- | --- |
| Handshakes accepted | 96.75% (2,890 of 2,987) |
| Frames sent by clients | 59,561 (152.7/s) |
| Frames received by clients | **9,730,675 (24,945/s)** |
| Connect p50 / p90 / p95 | 142ms / 1.28s / 1.64s |
| Message latency p50 / p95 | 1.21s / 19.46s |
| Peak `rtc_ws_connections` | 428 observed live (327 on A + 101 on B) |
| Data received | 3.6 GB |

The 163× amplification between frames sent and frames received is the fan-out
doing its job: every VU joins one conversation, so each send is broadcast to
every other connected member. 25k frames/s of delivery is the real figure here,
and the p95 message latency reflects k6 itself struggling to drain that on the
same machine as the servers.

The 3.25% of handshakes refused is worth a second look on real hardware before
being attributed to the service — at that moment the load generator, both
servers, PostgreSQL, Redis and the observability stack were sharing 16 threads.

`rtc_cache_hit_ratio` read 0.0 throughout. That is not a cache fault — none of
these scenarios exercise the `CacheService` read path, and `hit_ratio()` returns
0 for 0 hits and 0 misses.

The two rows worth believing are the JWT ones, and they carry the load-test
result: signing costs ~19µs and verification ~24µs, which is nothing next to the
bcrypt hash that made `auth.js` saturate. The authorization cache earns its place
— 275 ns cached against 1,724 ns cold is a 6× saving on a check that runs on
every authenticated request.

Database benchmarks (`BENCH_DB=1`, PostgreSQL 16 in Docker on the same host):
`BM_DbSelectOne` 2.89 ms, `BM_DbParameterisedQuery` 3.61 ms, `BM_DbFullTextSearch`
4.30 ms, `BM_DbMessageHistory` 3.46 ms, `BM_DbAuditAppend` 6.41 ms, and pool
acquisition at 128 ns single-threaded rising to 243 ns at four threads.

## Observations

**The database is the ceiling for messaging, and bcrypt is the ceiling for
authentication.** Those are two different limits with two different remedies:
more read replicas or a larger pool for the first, more CPU or a tuned cost
factor for the second. Neither is the application layer, which never exceeded
~130% CPU per instance on the messaging path.

**Memory is dominated by connections, not requests.** 806 MB against 40 MB
between two instances handling the same number of HTTP requests, differing only
in how many WebSockets they held. Capacity planning should size on concurrent
sockets.

**Nothing was dropped and nothing 5xx'd.** Zero dropped events, zero handler
failures, zero 5xx across 91,220 requests, ~442k cluster publishes and 9.7M
delivered frames. Under saturation the service got slower; it did not get wrong.

**What I would change first:** raise `DB_POOL_SIZE` from 8 and re-run
`messaging.js`. If throughput moves, the pool was the constraint rather than
PostgreSQL itself, and that is a one-line change.


## Known distortions

Everything here is co-located on one laptop, which makes the latency numbers
pessimistic and the throughput numbers unrepresentative in both directions.

- [x] Load generator on the same host as the service — it competes for the same 16 threads
- [x] Database on the same host
- [x] Redis, Prometheus, Grafana and Jaeger also on the same host
- [x] Small dataset — query plans differ at scale, and the whole working set fits in cache
- [x] Loopback networking (no real latency, no packet loss)
- [ ] `ulimit -n` not raised for high WebSocket counts
- [x] Tracing enabled at `sample_ratio=0.05`
- [x] CPU governor not pinned to `performance`
